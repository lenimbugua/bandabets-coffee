### Task 1: Banner `sizes` — stop shipping 960w to phones

**Files:**
- Modify: `app/components/TheBanner.vue:27-30` (the `sizes` prop default)
- Modify: `app/components/DesktopSportsLayout.vue` / `app/components/MobileSportsLayout.vue` ONLY IF they pass an explicit `sizes` prop to `<LazyTheBanner>` (check first; if they don't, leave them).

**Interfaces:**
- Produces: nothing consumed by later tasks.

Background: `.banner-slide` is `width: calc((100% - 0.75rem) / 1.1)` under 1024px, inside a page container with `px-2` padding (0.5rem × 2 = 1rem total; verify the actual mobile wrapper's horizontal padding by reading `app/layouts/default.vue` small-screen branch and `MobileSportsLayout.vue` before finalizing the calc — if padding differs from 1rem, adjust the subtracted constant to match and note it in the report). On ≥1024px the slide is 100% of the existing `min(1000px, calc(100vw - 664px))` container, which the current default already handles.

- [ ] **Step 1: Change the default `sizes` prop**

In `app/components/TheBanner.vue`, replace:

```js
const props = defineProps({
  sizes: {
    type: String,
    default: "(min-width: 1024px) min(1000px, calc(100vw - 664px)), 100vw",
  },
});
```

with (adjusting `1.75rem` = container padding 1rem + gap 0.75rem if the measured padding differs):

```js
const props = defineProps({
  // Mobile: the visible slide is (container − 0.75rem gap) / 1.1 wide
  // (see .banner-slide below) inside a 1rem-padded page — telling the
  // browser 100vw made it fetch the 960w rendition on ~400px phones;
  // the true ~85vw resolves to the 640w file (−46 KiB on the LCP path,
  // per the 2026-08-31 PSI report).
  sizes: {
    type: String,
    default:
      "(min-width: 1024px) min(1000px, calc(100vw - 664px)), calc((100vw - 1.75rem) / 1.1)",
  },
});
```

- [ ] **Step 2: Verify the preload matches**

The `useHead` preload uses `imagesizes: props.sizes` — confirm no other literal `100vw` remains in the file (`grep -n "100vw" app/components/TheBanner.vue` → only the new calc line).

- [ ] **Step 3: Build and verify rendition selection**

Run: `pnpm build 2>&1 | tail -3` → success.
Run: `PORT=3131 node .output/server/index.mjs & sleep 4; curl -s http://localhost:3131/ | grep -o 'imagesizes="[^"]*"' | head -2; curl -s http://localhost:3131/ | grep -o 'sizes="[^"]*"' | head -3; kill %1` → every occurrence shows the new calc, none show bare `100vw`.
Arithmetic check (record in the report): at 412 CSS px viewport, DPR 1.75 → `(412 − 28) / 1.1 × 1.75 ≈ 611` device px → the browser's srcset picker (640 ≥ 611) selects `…-640.webp`, not 960.

### Task 2: Shrink the render-blocking stylesheet (measure → decide → implement)

**Files:**

- Possibly modify: `app/assets/css/style.css` (only to remove verifiably dead rules found by the measurement — never design-system layers 1–3)
- Possibly modify: component `<style>` blocks or static-import graphs identified as entry-CSS contributors (list them in the report)

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces: the home page's render-blocking CSS budget for Task 4 to verify.

Current state: `entry.CfbhoblA.css` is 302,878 bytes raw / ~38 KB gzip and is the only stylesheet — every component whose CSS lands in the entry graph ships render-blocking on every page. PSI attributes 600 ms of Slow-4G blocking to it.

- [ ] **Step 1: Attribute the bytes**

Build with a manifest inspection: after `pnpm build`, use Vite's client manifest (`.output/server/chunks/` is not needed — read the client manifest JSON under `node_modules/.cache/nuxt/.nuxt/dist/client/_nuxt/` or `.output/public/_nuxt/` + the `builds` manifest, whichever exists; the `build:manifest` hook in `nuxt.config.js` already shows how chunk metadata is accessed) to list which modules' CSS was concatenated into the entry stylesheet. Cross-check by searching `entry.*.css` for distinctive class strings from candidate components (e.g. scoped `data-v-` hashes mapped back via `grep -rl "<style" app/components app/pages | xargs grep -l scoped`, then matching each file's compiled hash found in `.output`). Produce a table in the report: contributor → approx bytes → rendered on mobile home above the fold? (yes/no).

- [ ] **Step 2: Decide against the gate**

Gate: home-page render-blocking CSS ≤ 25 KB gzip with ≤2 stylesheets, CLS unchanged, no flash-of-unstyled-content on any of `/`, `/share-bets`, `/join-affiliate`, `/casino-home`.
- If ≥ ~30% of entry CSS belongs to components/routes NOT rendered on the home/sports path → implement **eviction**: stop force-merging those chunks' CSS into the entry (adjust the `build:manifest` hook's stripping rules and/or convert the responsible static imports to dynamic/`Lazy` so their CSS rides their own chunk, loaded on navigation). Their CSS must still load on the pages that need it — verify each affected route visually renders styled.
- Else (the CSS really is mostly global) → implement **defer-noncritical**: keep `app/assets/css/style.css` render-blocking but move the largest non-critical, self-contained blocks (e.g. festive/animations/rare-page utilities identified in Step 1) into a second stylesheet loaded with `media="print"` + `onload="this.media='all'"` and a `<noscript>` fallback via `app.head`. Hand-curate ONLY whole self-contained blocks, never token layers.
- If neither path can reach the gate without new tooling, STOP and report `BLOCKED: needs critical-CSS tooling decision`.

`pnpm build`; `ls .output/public/_nuxt/*.css | wc -l`; gzip-measure the render-blocking set referenced by the home HTML (`curl` the built server's `/` and list `<link rel="stylesheet">` hrefs; gzip each).
